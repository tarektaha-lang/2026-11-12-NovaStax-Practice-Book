What this stage does

Given a book id, split.py reads that book's XML table of contents, checks it for the mistakes that would otherwise surface as silently wrong output, and then walks every leaf section of the book. For each (source PDF, section) pair it renders the pages the section claims to JPEG, crops the first and last page to the fractional boundaries the XML gives them, and writes the JPEGs into a freshly hand-built one-image-per-page PDF under data/temp/<book_id>/01_sections_pdf/.

The rendered images are never kept on disk. The section PDFs are the only artefact, and everything downstream reads them rather than the original textbooks.

Inputs and the table of contents

A book lives in one directory named after its id. That directory holds the source textbook PDFs, named by their md5, and one XML file with the same name as the directory. Three books are checked in: eg_mathematics_en_g4_t2 (3 source PDFs, 17,641 bytes of XML), eg_mathematics_en_g7_t1 (2 source PDFs, 5,091 bytes) and eg_mathematics_en_g8_t1 (2 source PDFs, 5,214 bytes).

The XML is a nesting of <module> elements under a single <book> root. Only the innermost modules — the leaves — carry <source> children, and each source names one textbook PDF by md5 plus the page range the section draws from it.

<book subject="Mathematics" grade="8" term="1" language_code="en" language="English"
      subject_id="" academic_year="25-26" country_code="eg" country="Egypt">

            <source md5="e43cddae8de6a01b542c089e25c02368" start_page="8" end_page="19"/>

Page numbers and fractional boundaries

Page values are mapped onto one linear axis by page_position so that ranges can be compared and overlap-checked. A whole number in end_page means the end of that page, so end_page="12" becomes 13.0 internally and page 12 is included in full. A fractional value is an explicit position part-way down a page: 19.4 is 40% of the way down page 19. That is how two consecutive sections share one physical page, one ending where the other begins.

Validating the table of contents

Validation runs first unless --skip-validation is given, and it reports every problem it finds rather than stopping at the first. Two failures are fatal on their own — a missing XML file and XML that is not well-formed — and return immediately. Otherwise the parsed tree is read into Span objects by collect_spans, which contributes its own errors for malformed attributes, and then six independent checks run over the result. Each error string is prefixed with a bracketed tag naming its origin, so a long report can be read by category.

FunctionTagWhat it rejects
collect_spans[attrs]A <source> with no md5, missing start_page or end_page, or a non-numeric page value. The offending source is dropped, so it takes no part in the later checks.
check_level_progression[levels]A module whose level attribute does not match its nesting depth. Levels must start at 1 and increase by exactly 1 per step inwards.
check_sources_on_leaves[placement]A <source> that is a direct child of <book>, and a module that holds sources while also nesting further modules.
check_page_order[order]A span that runs backwards. The mapped positions catch most of them, but a whole number in end_page means the end of that page, so 20 to 19 maps to the single point 20.0 and looks empty rather than descending; the raw attribute values are therefore compared as well. 19.4 to 19 is not backwards — it is the last 60% of page 19.
check_no_empty_spans[empty]A span whose start and end resolve to the same point, leaving no height to render. A whole number repeated on both sides is that page in full and is accepted; a fraction repeated on both sides — 19.4 to 19.4 — is not. The raw values must agree too, so a backwards range landing on one point is reported by [order] alone and no span is reported by both checks.
check_no_overlaps[overlap]Two spans on the same md5 that overlap. Ranges that merely touch at a shared boundary are accepted, since that is exactly how a shared page is split.
check_pdfs[pdf]A referenced PDF that is missing, unreadable, or shorter than the highest page any section asks of it. Page counts here come from pypdf.

Success prints one line and the run continues into the split. Failure prints a count and every problem to standard error, and the process exits 1 without rendering anything.

Why pages are rasterised

Rasterising every page is a deliberate choice, not a shortcut. A section can begin or end part-way down a page, which means the page it shares with its neighbour must reach the model carrying only one section's half.

The obvious way to do that in PDF is a CropBox: keep the page, narrow the visible window. Two measurements taken while this stage was being designed ruled that out and settled the output format at the same time — the first showed a CropBox does not hide vector text from the model, the second showed that a page inside a PDF costs about half the tokens of the same image sent loose. Both are recorded below with the method that produced them.

One mechanism for both kinds of page. The source textbooks mix born-digital pages that carry a real text layer with scanned pages that do not. Rasterising treats both identically, so the correctness of a boundary does not depend on how the page happened to be produced.

Finding: a CropBox does not hide vector text

Two sets of four hand-built one-page PDFs, every page 400 x 800 pt, each carrying something in the region a crop was supposed to hide. The vector set drew ZEBRAWORD near the top of the page and MANGOWORD near the bottom. The raster set drew one full-page image instead, solid red over the top 70% and solid blue over the bottom 30%. Within each set the four variants were the same: no crop at all; a CropBox narrowed to the bottom 30% with the full-height content left in place; the excluded content genuinely absent from the content stream, page size unchanged; and the excluded content absent with the page shrunk to the strip that was kept. Each PDF was sent inline on its own, with a prompt asking the model to list every distinct capitalised word, or every solid colour, it could find anywhere on or around the page, explicitly including anything faint, cut off or outside the visible area.

The vector run was first written against gemini-3-pro-preview and repeated once the model name was brought in line with the rest of the project; the answers above are from the gemini-3.6-flash run. Two local checks on the same files agree with the split: pypdf's extract_text() also returned ZEBRAWORD through the narrowed CropBox, while pypdfium2 rendered the narrowed raster file as pure blue at 400 x 240 px.

Only one cell leaked, and it is the cell that matters: a narrowed CropBox over vector text. So the leak belongs to the native text channel, which walks the page's text objects without regard for the visible window, and not to the vision path, which honours it. Both hard variants held for both content types. Rendering each page to an image and discarding the unwanted pixels is the hard variant applied unconditionally — it removes the text layer entirely, so a boundary stays correct without the pipeline having to know whether the source page carried text.

Finding: a PDF page costs about half an inline image

One page of a checked-in source textbook was rendered at this stage's own 3072 px cap and JPEG-encoded at quality 85, then sent to the model twice: once as an image part, once as the only page of a one-page PDF built around those same bytes. Transport was inline both times and the prompt was the same one-word request, so the container was the only thing that differed. The figure compared is prompt_token_count from the reply's usage metadata.

Measured during project development on 15 August 2026 against gemini-3.6-flash, on a single 2087 x 3072 px page with media_resolution left at its default: a factor of 2.01 for identical pixels. The mechanism is that an image part is tokenised by tiling while a document page is billed per page, which Google's documentation puts at 258 tokens. One page on one model is thin evidence for an exact ratio, so treat the halving as the approximate size of the effect rather than a rate to project a budget from; the direction is what this stage is built on.

That is why this stage produces PDFs rather than loose image files, even though the PDF it writes contains nothing but one image per page.

Neither experiment survives in the repository. The crop test lived in scripts/_crop_experiment/ and was deleted once its results were in; the token comparison was a one-off command that was never saved as a file. The numbers on this page are the only record of both, so re-checking either one means rebuilding the test documents from the method described above, and it means paying for API calls that nothing else in this stage needs.

Rendering, cropping and assembly

Each page goes through render_page, then a group of pages goes through write_image_pdf.

Render

The scale is chosen so the page is 3072 px tall, and clamped so that a landscape page's width lands on 3072 px instead. The model scales a document page to at most 3072 px on a side and gains nothing from more, so that cap is the target rather than a compromise. The rendered image is converted to RGB and, if this is a cropped boundary page, hard-cropped to the [top, bottom] slice before a single JPEG encode at quality 85.

Assembly

write_image_pdf writes the PDF by hand rather than through a library. It emits a %PDF-1.4 header, a catalog as object 1, a page tree as object 2, then three objects per page — the page, its content stream, and the image XObject — followed by a real xref table and trailer. Each page's MediaBox is the source page's width and its cropped height in points, so the section PDF keeps the original physical scale of the page.

The JPEG bytes are embedded verbatim. The image XObject declares /Filter /DCTDecode and the encoded JPEG is written straight into the stream. No PDF library decodes and re-encodes it, so the single encode inside render_page is the only lossy step in the whole pipeline.

Rebuilding is deterministic: re-running the same section with --update produced byte-identical files, verified by md5 before and after.

Exit codes

  • 0. Validation passed, or was skipped, and the split completed.
  • 1 from validation. FAILED: <book_id> has N problem(s) to standard error, followed by one indented line per problem. Nothing is rendered.
  • 1 from the split. Any RuntimeError raised while splitting is caught in main, printed as FAILED: <message> to standard error, and turned into exit 1. There are two such errors: no section 9.9 in eg_mathematics_en_g8_t1 when -s names a section the book does not have, and missing source PDF: <path>, which validation would normally have caught first and so is only reachable under --skip-validation.
Open source PDFs are always closed. Source documents are opened lazily, at most once per md5, cached for the whole run, and closed in a finally block, so an error part-way through a book does not leave handles open.

When a section PDF is skipped

The skip rule is deliberately narrow. A section PDF is skipped when both of these hold:

  1. The output file exists and can be opened.
  2. Its page count equals the number of pages the XML implies for that (source, section) pair.

Anything else — a missing file, an unreadable one, or one whose page count no longer matches because the table of contents changed — is rebuilt. --update forces a rebuild regardless. The count on disk is read with pdf_page_count, which returns None for a file that is missing or that pypdfium2 refuses, and None never equals the expected count, so both cases rebuild.

No timestamps are compared, on purpose. The project lives in a Dropbox folder, where modification times are not trustworthy: a sync can rewrite mtime without the content changing, and can restore old content with a fresh mtime. Comparing the source PDF's mtime to the output's would therefore rebuild work that is fine and skip work that is stale. Page count is derived from the content itself and survives syncing.

The trade-off is that an edit which changes a section's boundaries without changing how many pages it covers — moving a fractional split from 49.30 to 49.50, say — is not detected. Such an edit needs --update.

Sizes and the 50 MB ceiling

The model refuses documents past 50 MB, and that refusal only surfaces at upload time, well after this stage has finished. So every built PDF is measured and any file over SIZE_WARN_BYTES — 45 MB — has WARNING: close to the 50 MB the model accepts appended to its progress line. The 5 MB margin leaves room for a section to grow before it becomes a hard failure downstream.

In practice the checked-in books are far from the limit. The largest single file in the sample book is 10.48 MB and the mean is 4.45 MB.

Requirements

Three third-party packages are imported, all pinned in requirements.txt at the project root. A missing one is caught at import time and reported as missing dependency (<name>): pip install -r requirements.txt rather than a traceback. The standard library supplies everything else: argparse, io, math, sys, xml.etree.ElementTree, dataclasses and pathlib.
