What the script does

A practice book is assembled section by section, and a section usually appears in more than one source textbook. specs.py reads the image-only section PDFs that stage 1 produced, hands all of a section's PDFs to the model in a single call, and stores the reply as a lesson section spec: what the section teaches, the objectives it serves, the fences around it, and the wording later writing has to reuse. Nothing here writes teaching prose — a spec is a brief for whatever writes the study book next.

The shape of the work

  • One section, one call. Every source PDF for a section goes into the same request, so the model sees all treatments of the topic at once and can reconcile them itself.
  • One section, one file. The output is named by zero-padded hierarchy alone — 01_01.json for section 1.1 — with no book or source identifier in the name, because there is nothing to disambiguate.
  • Schema-enforced. Pydantic models are handed to the Gemini SDK as a response schema, and the reply is validated again on the way back with SpecReply.model_validate_json.
  • Self-contained output. The book's own metadata travels with every spec, so a downstream reader needs nothing but the one JSON file.
  • Resumable. A section already holding a spec of the current shape is skipped without touching the network.

Where it sits in the pipeline

Stage 1 is split.py, which validates a book's table of contents and rasterises every page a section claims into an image-only PDF, one per (source PDF, section) pair, under 01_sections_pdf/. specs.py reads those files and writes 02_section_specs/. It never reads the original textbook PDFs, and it never rebuilds a section PDF: if one is missing it stops and tells you to run stage 1 first.

specs.py borrows the pipeline's shared vocabulary rather than re-deriving it. From split.py it imports PROJECT_ROOT, TEMP_DIR, SECTIONS_STAGE, Span, book_root, book_spans, book_metadata, section_spans, number_pad_width, number_stem and section_stem; from api_logger.py it imports ApiLogger, safe_log, genai_answer_text, genai_response_files and genai_usage. The zero padding is derived, not fixed: number_pad_width returns max(2, len(str(largest number in the TOC))), which is 2 for the sample book, so 1.1 becomes 01_01.

What one run does

build_specs resolves the book once — its TOC root, its metadata, its padding width, the two stage directories and the filled prompt — then decides in table-of-contents order which sections still need specifying, checks the inputs for all of them, and hands the survivors to a pool of workers.

  1. Decide, section by section. Compute each output path from the padded hierarchy and, unless --update was given, drop the section when written_spec says a current-shaped file is already there. What is left is the pending list.
  2. Locate every input, before any call. Each pending section's PDFs are looked for up front. Any section short of even one of them stops the run with N section(s) have no PDF: <numbers>; run split.py first. This happens before the first call because sections run together: otherwise a book that was never split would spend a whole set of calls before the first missing file stopped it.
  3. Build the client and logger, once. If anything is pending, construct genai.Client() and ApiLogger(TEMP_DIR / book_id) and gather them, with the rest of the book-wide values, into a frozen Run.
  4. Fan out. A ThreadPoolExecutor of min(len(pending), MAX_WORKERS) threads runs specify_section per section.
  5. Collect. as_completed yields each section as it lands; the driver counts it, prints its line, and carries on.

Each worker uploads its section's PDFs, calls the model through request_spec until a reply validates, deletes its uploads in a finally block, and either writes the numbered spec or reports an abort. It returns the line to print rather than printing it, so two workers finishing together cannot interleave half a line each.

Nothing to do means no network. Both the Gemini client and the logger reach out when constructed — ApiLogger.__init__ queries an NTP server to timestamp its folders accurately, retrying up to ten times before giving up with a RuntimeError. Both are built only if the pending list is non-empty, so a run whose sections are all already specified makes no network access at all. That is what makes the skip path usable offline, and it is also why a full-book re-run is cheap to attempt. Building them once, outside the pool, also means the logger's clock is synchronised a single time rather than once per worker.
Lines arrive out of order. Sections are printed as they complete, not in table-of-contents order, because a five-page section finishes well before a twenty-eight-page one that started at the same moment. Every line names its section, and the closing OK: line reports the totals.

Each written section prints a one-line summary from describe, which reports only the counts that are non-zero, and the run closes with an OK: line naming the stage directory relative to the project root:

$ python scripts/specs.py -s 1.1 eg_mathematics_en_g8_t1
OK: 0 section spec(s) written, 1 already specified under data/temp/eg_mathematics_en_g8_t1/02_section_specs

Real output, section 1.1 of eg_mathematics_en_g8_t1 already specified; the run made no API call. The , N already specified and , N aborted clauses are appended only when those counts are non-zero.

When a section is skipped

A section is skipped when --update was not given and written_spec(out_path, envelope_keys) returns true. That function is stricter than validation alone, and deliberately so: Pydantic ignores unknown keys and fills absent arrays from their empty defaults, so a file written before a field was renamed would validate happily while holding the old name. All four of the following must hold.

CheckHow
The file exists and parses as JSON json.loads(path.read_text(encoding="utf-8"))
Its top-level keys are exactly the envelope keys expected today set(document) == envelope_keys
Its spec body keys are exactly the current spec fields set(document["spec"]) == set(SectionSpec.model_fields)
The body validates against the live schema SectionSpec.model_validate(document["spec"])

Any OSError, LookupError, TypeError or ValueError along the way — which covers a missing file, a truncated write, a missing spec key and every Pydantic validation error — is caught and read as "absent", so the section is simply specified again. envelope_keys is built per book as {"book_id", *meta, "number", "title", "module_path", "spec"}, which is 14 keys for the sample book: the five fixed ones plus its nine metadata attributes.

The check is shallow, on purpose. It compares the top-level envelope keys and the spec body keys, and nothing deeper. It never looks at the keys inside a row. If a nested row field is added or removed — a new field on teaching_points[], say, or a dropped one on excerpts[] — existing files still match at both levels it inspects, still validate (the new field would take its default, the removed one is ignored as unknown), and are therefore not detected as stale. After any change to a nested model, rebuild with --update. This is a known, accepted trade-off: a deep comparison would have to mirror the model tree, and the top-level check already catches the common case of the spec's own field set changing.

How the PDFs reach the model

upload_pdfs puts every section PDF behind a file URI: each one is uploaded with client.files.upload, polled to readiness, referenced as a types.Part.from_uri, and deleted once the answer is in. There is no size test and no second transport. Nothing is ever sent inline.

This is a choice rather than a limit. The API would take these documents inline comfortably — as of August 2026 an inline payload may reach 100 MB, or 50 MB for PDFs, and the largest section either sample book has ever produced is 18.2 MB across its two sources. Uploading buys three things instead:

  • Memory. Inline transport reads the whole PDF into memory and holds it there for the length of the call. With up to MAX_WORKERS = 100 sections in flight at once, that is the difference between streaming a file from disk and holding a hundred of them in RAM beside each other.
  • Cheaper retries. A retried attempt re-sends a URI, not the bytes. Inline, all four attempts would carry the full payload again.
  • One path, always exercised. A size-triggered branch is by definition the code that runs least and breaks most quietly. On the g7 book it fired for exactly one section in sixteen.

What it costs is a round trip before the call and an obligation afterwards: an upload occupies the project's 20 GB Files quota until it is deleted or until it expires on its own after 48 hours. specify_section deletes in a finally block, so the handles go whether the call succeeded, aborted or raised. Transport does not affect the bill — the same section specified both ways was charged an identical 14,915 input tokens.

wait_until_ready polls a handle every UPLOAD_POLL_SECONDS = 2.0 seconds until its state reads ACTIVE. A state of FAILED raises immediately, and a handle still not ready after UPLOAD_READY_TIMEOUT = 120.0 seconds raises with the state it was last seen in.

The upload is retried, and partial uploads are cleaned up. Every section now depends on an upload, so a single failed transfer would otherwise cost a section all four of its model attempts before it ever made one. upload_pdfs therefore retries the whole set up to MAX_ATTEMPTS = 4 times with the same 2 s, 4 s, 8 s backoff the model calls use. Because uploads are made one at a time, a failure on the second PDF leaves the first sitting in the account holding quota, and nobody else holds that handle: each failed attempt calls delete_uploads on whatever went up before giving up or trying again. delete_uploads swallows its own errors, since an upload that cannot be deleted expires by itself and that is not worth failing a run over.

Verified on section 4.6 of eg_mathematics_en_g7_t1, specified once each way: 14,915 input tokens both times, and a count of the PDFs held server-side read zero before the run and zero after it.

Retries, aborts and failure

request_spec loops up to MAX_ATTEMPTS = 4 times. One attempt covers both the transport and the parse — logged_call catches every exception from generate_content and from SpecReply.model_validate_json alike, records the failure as "{type}: {message}", and returns None. Between attempts the loop sleeps 2 ** attempt seconds, so 2 s, 4 s and 8 s; there is no sleep after the last attempt. When all four fail it raises failed after 4 attempts: <last error>. upload_pdfs retries on the same schedule before the call is ever made.

A section that exhausts its attempts no longer ends the book. The driver catches whatever the worker raised, reports that one section, and lets the others finish — sixteen sections running together should not all be lost to the one that failed. Those failures are counted and returned, so the exit code still reflects them.

OutcomeConsoleExit
All sections written or skipped OK: ... under data/temp/<book_id>/02_section_specs 0
The model returned status: "abort" for at least one section 1.1: aborted, <reason> — then the OK line with an , N aborted clause 1
A section raised — four failed uploads or four failed calls 1.1: failed, <type>: <message> — then the OK line with a , N failed clause 1
A RuntimeError before the pool — no API key, unknown section, missing section PDFs, unreadable prompt, or a TOC leaf that is not unique FAILED: <message> on stderr 1

An abort is a judgement, not a fault: it is counted, printed, and the exit code is 1 purely so a caller notices. The last row is the only kind that stops a run outright, and every check in it runs before the first call goes out, so nothing is spent on a book that cannot be specified.

The prompt and the combine rules

The prompt lives beside the script at scripts/specs.md, 125 lines of it, and it is half the behaviour. build_prompt reads the file and substitutes a single placeholder, {book_context}, by hand rather than with string.Template — the prompt is full of LaTeX and Template would read every $ in it as a placeholder. A missing file or a missing placeholder is a RuntimeError. For the sample book the substituted line reads:

Subject: Mathematics | Grade: 8 | Term: 1 | Language: English | Language code: en | Country: Egypt

A second text part carries the course around the section. course_toc walks the TOC into a titles-only tree and flags the leaf being specified with "current": true; it raises unless exactly one leaf is marked, which catches both a bad section argument and a malformed TOC. toc_part labels it so the model can tell it from the prompt:

Combine-only, and what that means

This is the heart of the stage. Multiple PDFs for one TOC leaf are multiple textbooks teaching the same thing, and the prompt asks for our single-voice section rather than a collage: not source-labelled, free to rechunk and rewrite, but with every content item still grounded in at least one PDF.

  • Semantic union, called absolute. For glossary, teaching_points, excerpts, equations and notations: two items carrying the same meaning, even in different wording or with different emphasis, collapse to one row, keeping the clearer or more complete version. A second row is added only when it teaches or reprints something substantively different. The same applies one level down, to a teaching point's nested figure: one visual idea, one figure on the surviving point.
  • Objectives are reconciled, not unioned. They follow a dedicated two-step rule. First seed: where a PDF prints its own learning objectives, start from those printed lists, collapsing same-meaning rows and taking the semantic union where the lists differ; where no PDF prints any, infer them from the content. Then reconcile against the synthesised section: drop any seeded objective the content does not actually tackle, and add any outcome the content clearly teaches that the printed lists missed. The result is the section's objectives, not a bibliographic merge of publisher boxes.
  • Depth is chosen, not averaged. Where two books treat the same point at different depth, one notes block covers what both support; a deeper treatment from one book is included only if it belongs in our section, and otherwise becomes an out_of_scope row. Blurring into vague averaged prose is called out as the failure mode to avoid.
  • Excerpts stay exact. Where books print near-equivalent wording, one source is chosen — most complete conditions and conclusion first, then clearer standard school wording, then whichever prints the conventional name — and copied once, character for character. Never one row per book, never a synthesised paraphrase.
  • Order is instructional. With one PDF the content arrays follow first appearance. With several they follow a coherent order for the synthesised section: dependency before dependents, definition then property then application then converse, rather than "PDF 1 then PDF 2".

Topical mismatch and the abort path

The reply envelope is SpecReply: status ("ok" or "abort"), abort_reason (empty when ok) and spec. Abort is reserved for a hard topical mismatch — a PDF that is clearly a different topic from the TOC leaf, the prompt's example being a leaf on kinetic energy with a PDF mostly about acids and alkalis. A different approach or a different depth on the same topic is not an abort; a single PDF is never an abort; borderline same-topic cases resolve to ok without deliberation. Because spec is a required field of the envelope even when aborting, the prompt specifies a minimal schema-valid shell — role teach, a placeholder overview, one placeholder row in each of the three arrays the schema requires, empty lists elsewhere — and forbids inventing real teaching content in it. The script never writes that shell to disk.

The rest of the prompt sets the boundaries the schema cannot: stay in the book's language and never translate or synonym-swap a term, keep Arabic tashkeel and underlines exactly as printed in verbatim fields, omit any claim resting on an illegible page, and never write the study book itself.

The spec schema

SectionSpec is handed to the SDK as the response schema, nested inside SpecReply, and used again to validate the reply and to check existing files on the skip path. It has exactly ten fields, declared in the order they are written to disk: what the section is, then what it must achieve, then the material it teaches with.

FieldTypeRequiredWhat it holds
role "teach" | "revision" | "assessment" yes What kind of section this is. teach covers instructional material including labs that teach content.
overview str yes Four to eight analyst sentences on the section's pedagogical arc, including notable activity patterns. Not student prose.
objectives list[Objective] yes, min 1 Observable learner outcomes, seeded from printed objectives then reconciled against the content.
prerequisites list[Prerequisite] yes, min 1 Skills and knowledge the section assumes, written as skill statements and never as unit titles or grade labels.
out_of_scope list[OutOfScope] yes, min 1 Near-miss topics and alternate approaches this section must not teach, each with a reason.
glossary list[GlossaryEntry] no, defaults to [] Terms with a short gloss in the book's language.
teaching_points list[TeachingPoint] no, defaults to [] The teachable ideas, skills, processes and structures, each with enough notes to teach it without the PDFs.
excerpts list[Excerpt] no, defaults to [] Wording copied from a source that later writing must reuse; empty when none.
equations list[Equation] no, defaults to [] Load-bearing symbolic relations in reusable general form, not filled numeric instances.
notations list[Notation] no, defaults to [] How to read the section's symbolic writing: what a symbol or unit stands for, how a form is written.

What the writer adds: ids and always-present arrays

spec_document converts the validated model into the dict that is written. It dumps with exclude_defaults=True, then walks SectionSpec.model_fields in declaration order. A field that is not in ID_PREFIXES — that is, role and overview, neither of which has a default — is copied straight through. Every other field is rebuilt as [{"id": f"{prefix}_{n}", **row} for n, row in enumerate(body.get(field) or [], 1)].

Two consequences fall out of that one rule, and both matter to a consumer:

  • Every array is always written, empty or not. exclude_defaults=True drops an array that still equals its empty default, and the body.get(field) or [] puts it back as []. A reader can count on all ten keys being present in spec.
  • Optional row fields are omitted, not written as defaults. The same exclude_defaults=True leaves figure out of the teaching points that do not have one, rather than writing "figure": null. It is currently the only optional field anywhere in the tree, so it is the only omission a reader will see.

Ids are assigned on the way to disk rather than by the model, so a later stage can cite objective_2 and mean the second objective written here. The prefix is the array name in the singular, with two that are not a mechanical singularisation:

The console line for that section, from describe, would read 1.1: 2 source(s) -> 5 objectives, 5 teaching points, 2 terms, 3 excerpts, 3 equations. It reports five of the eight arrays and drops any whose count is zero, so it is a progress signal rather than a full inventory.

API call logging

Every attempt is logged, successful or not, through safe_log — a wrapper that catches its own failures and prints a warning rather than losing a generation to a logging problem. ApiLogger creates one folder per call under data/temp/<book_id>/00_api_call_logs/, named {timestamp}_{item}_{step}, where the item is the dotted section number and the step is always section_spec. Timestamps come from an NTP server rather than the local clock.

FileContents
call.jsonTimestamp, item, step, attempt, api, model, token usage, duration, status, plus the extra context below.
prompt.txtThe filled prompt exactly as sent.
course_toc.txtThe labelled course TOC part.
response.jsonThe full SDK response dumped with exclude_none=True, from genai_response_files.
response_text.txtThe concatenated text parts, written only when the model returned text.

The PDFs themselves are not copied into the log — they already sit under 01_sections_pdf/, and call.json names them.

Beyond the standard fields, logged_call records the whole shape of the request: book_id, section, section_title, module_path, a sources list of md5 with start_page and end_page, the pdfs filenames, an uploaded flag saying which transport was used, prompt_file, thinking_level, and returned, which holds the model's own status or null when the attempt failed. Token usage comes from genai_usage: input_tokens, thinking_tokens, output_tokens and total_tokens, with any the API omitted dropped rather than written as null.
